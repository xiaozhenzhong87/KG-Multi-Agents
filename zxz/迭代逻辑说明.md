# 迭代逻辑和seed_ids累积机制详解

## 关键概念澄清

### Q1: 25*2条边是什么意思？
**A**: `25 * 2 = 50` 是Neo4j查询的**总限制**，不是每个节点25条。
- 查询会从**所有seed_ids**（这里是2个节点A和B）的邻居中返回**最多50条边**
- 实际返回数量可能少于50条（取决于数据库中的实际数据）
- 不是"基于两条边查询25个关系"，而是"基于2个seed节点，总共查询最多50条边"

### Q2: 50*2路径最终是50条还是100条？
**A**: `50 * 2 = 100` 是查询的**上限**，实际返回可能少于100条。
- 查询会从**所有seed_ids**的两跳路径中返回**最多100条路径**
- 如果数据库中只有50条符合条件的路径，就只返回50条
- 你的理解是对的：实际返回数量取决于数据，limit只是上限

### Q3: 迭代2的CDE是怎么来的？
**A**: CDE来自Agent的响应。
- 在迭代1中，Agent分析子图后，如果发现信息不足，会返回 `missing_information: ["C", "D", "E"]`
- 这些是Agent认为需要但当前子图中没有的**实体名称**（字符串）
- 然后通过`matcher.batch_match(["C", "D", "E"])`将这些名称匹配到知识图谱中的**节点ID**
- 匹配到的节点ID被添加到seed_ids中，用于下一次迭代

### 3.1 迭代开始（第257行）

### 3.2 获取子图（第258行）- **关键点1：使用累积的seed_ids**

```python
subgraph = self.retriever.fetch_subgraph(seed_ids)
```

**这里的问题**：每次迭代都使用**所有累积的seed_ids**来获取子图，而不是只使用新增的。

**子图获取逻辑**（`graph_tools.py` 第179-282行）：
- `_fetch_one_hop()`: 获取所有seed_ids的一跳邻居
  - **查询限制** = `max_neighbors * len(seed_ids)` = `25 * len(seed_ids)`
  - 这是Neo4j查询的**总限制**，从所有seed_ids的邻居中返回**最多**这么多条边
  - 实际返回数量可能少于限制（取决于数据库中的实际数据）
- `_fetch_two_hop()`: 获取所有seed_ids的两跳路径
  - **查询限制** = `max_two_hop_paths * len(seed_ids)` = `50 * len(seed_ids)`
  - 这是Neo4j查询的**总限制**，从所有seed_ids的两跳路径中返回**最多**这么多条路径
  - 实际返回数量可能少于限制（取决于数据库中的实际数据）

**累积效应示例**（假设每次都能返回接近限制数量的结果）：
- 迭代1: seed_ids = [A, B] → 查询限制 25*2=50 条边 + 50*2=100 条路径（实际可能返回更少）
- 迭代2: seed_ids = [A, B, C, D, E] → 查询限制 25*5=125 条边 + 50*5=250 条路径（实际可能返回更少）
- 迭代3: seed_ids = [A, B, C, D, E, F, G, H, I, J] → 查询限制 25*10=250 条边 + 50*10=500 条路径（实际可能返回更少）

**注意**：即使实际返回的数量少于限制，随着seed_ids数量增加，查询的**潜在结果集**仍然在增长，因为查询会扫描更多节点的邻居。

### 3.4 处理Agent响应（第283-307行）

#### 3.4.1 JSON解析流程

**步骤1: LLM返回JSON字符串**
- `run_json_prompt()` 调用LLM，LLM根据prompt要求返回JSON格式的字符串
- Prompt要求（`build_agent_payload()` 第197-204行）：
```json
{
  "status": "ANSWER" | "NEED_MORE_CONTEXT",
  "reasoning_chain": "string (must include CUI or node_id references for each entity)",
  "filtered_entities": [{"node_name": str, "node_id": str | null, "reason": str}],
  "answer": {"option": str, "text": str, "confidence": float} | null,
  "missing_information": ["entity or relation names"]
}
```

**步骤2: 提取并解析JSON**（`deepseek_client.py` 第78-99行）
```python
# run_json_prompt() 内部执行：
raw_text = self.run_prompt(...)  # 调用LLM API，获取原始文本
json_text = self._extract_json_block(raw_text)  # 从文本中提取JSON块
agent_output = json.loads(json_text)  # 解析为Python字典
```

`_extract_json_block()` 的逻辑（第122-136行）：
- 如果文本以`{`开头且以`}`结尾，直接返回
- 如果文本以`[`开头且以`]`结尾，直接返回
- 否则使用正则表达式查找JSON块：`r"(\{.*\}|\[.*\])"`（使用`re.DOTALL`标志，`.`可以匹配换行符）
- 如果找不到JSON块，抛出异常

**步骤3: parse_agent_response()**（第208-211行）
```python
def parse_agent_response(payload: Any) -> Dict[str, Any]:
    if isinstance(payload, dict):
        return payload  # 直接返回字典（因为run_json_prompt已经解析好了）
    return {}  # 如果不是字典，返回空字典
```

**注意**：`parse_agent_response()` 函数非常简单，因为真正的JSON解析工作已经在 `run_json_prompt()` 中完成了。这个函数只是一个安全检查，确保返回的是字典类型。

**完整流程图**：
```
LLM API调用
    ↓
返回原始文本（可能包含markdown代码块、说明文字等）
    ↓
_extract_json_block() 提取JSON块
    ↓
json.loads() 解析为Python字典
    ↓
run_json_prompt() 返回字典（agent_output）
    ↓
parse_agent_response(agent_output) 安全检查
    ↓
返回parsed字典（包含status, missing_information等字段）
    ↓
parsed.get("missing_information") 提取字段
    ↓
过滤出字符串类型的项 → needed列表
```

#### 3.4.2 提取missing_information（第307-309行）

```python
parsed = parse_agent_response(agent_output)  # parsed已经是字典了
status = (parsed.get("status") or "").upper()  # 获取状态

# 提取missing_information字段
missing_info = parsed.get("missing_information") or []  # 获取列表，默认为空列表
needed = [item for item in missing_info if isinstance(item, str)]  # 过滤出字符串类型的项
```

**处理逻辑**：
- `parsed.get("missing_information")` 从字典中获取 `missing_information` 字段
- 如果字段不存在或为None，使用空列表 `[]`
- `[item for item in missing_info if isinstance(item, str)]` 过滤出所有字符串类型的项（忽略其他类型）

**示例**：
- 如果LLM返回：`{"missing_information": ["diabetes", "insulin", "glucose"]}`
- 则 `needed = ["diabetes", "insulin", "glucose"]`
- 如果LLM返回：`{"missing_information": ["diabetes", 123, null, "insulin"]}`
- 则 `needed = ["diabetes", "insulin"]`（过滤掉非字符串项）

- `"ANSWER"`: 可以回答问题，结束迭代
- `"NEED_MORE_CONTEXT"`: 需要更多信息，继续迭代

### 3.6 如果Agent需要更多上下文（第307-344行）- **关键点2：seed_ids累积**

```python
# 步骤1: 提取Agent请求的缺失信息
missing_info = parsed.get("missing_information") or []
needed = [item for item in missing_info if isinstance(item, str)]
# 例如: needed = ["bronchodilator", "corticosteroid"]

# 步骤2: 将请求的实体名称匹配到知识图谱节点
matches = self.matcher.batch_match(needed)

# 步骤3: **将新匹配的节点ID添加到seed_ids中（累积！）**
new_ids = []
for query_name, result in matches.items():
    for node in result.matches:
        node_id = node.get("cui") or node.get("id")
        if node_id and node_id not in seed_ids:
            seed_ids.append(node_id)  # ⚠️ 这里累积：旧的seed_ids保留，新的添加进去
            new_ids.append(node_id)
```

**累积示例**（说明CDE的来源）：
- **迭代1前**: seed_ids = [A, B] （从问题中提取的实体）
- **迭代1中**: Agent分析子图后，返回 `missing_information: ["C", "D", "E"]` （Agent认为需要但子图中没有的实体名称）
- **迭代1后**: 通过`matcher.batch_match(["C", "D", "E"])`匹配到节点，假设匹配到：
  - "C" → 匹配到节点 [C1, C2]
  - "D" → 匹配到节点 [D1]
  - "E" → 匹配到节点 [E1, E2]
  - seed_ids = [A, B, C1, C2, D1, E1, E2]  ← 新增了C1, C2, D1, E1, E2
- **迭代2前**: seed_ids = [A, B, C1, C2, D1, E1, E2]  ← 包含所有之前的
- **迭代2中**: Agent返回 `missing_information: ["F", "G"]`
- **迭代2后**: 匹配后，seed_ids = [A, B, C1, C2, D1, E1, E2, F1, F2, G1]  ← 又新增了F1, F2, G1
- **迭代3前**: seed_ids = [A, B, C1, C2, D1, E1, E2, F1, F2, G1]  ← 包含所有之前的

## 4. 问题根源分析

### 4.1 seed_ids累积导致的问题

1. **子图查询规模增长**：
   - 每次迭代都查询**所有seed_ids**的邻居
   - seed_ids数量线性增长 → 查询结果指数增长

2. **子图文本长度爆炸**：
   - `format_subgraph_as_text()` 将所有节点、边、路径转为文本
   - 没有长度限制，导致token数量超过131072的限制

3. **重复查询**：
   - 每次迭代都重新查询所有seed_ids的邻居
   - 即使某些节点已经在之前的迭代中查询过

## 5. 数据流示例

假设一个问题需要3次迭代：

### 迭代1
- **输入seed_ids**: [A, B] (2个节点)
- **Neo4j查询**:
  - 一跳查询：`MATCH (seed:Entity)-[rel]-(neighbor:Entity) WHERE seed.cui IN [A, B] LIMIT 50`
  - 两跳查询：`MATCH (seed:Entity)-[rel1]-(mid:Entity)-[rel2]-(neighbor:Entity) WHERE seed.cui IN [A, B] LIMIT 100`
- **查询限制**: 最多50条边, 最多100条路径（这是上限，实际可能更少）
- **实际返回**: 假设数据库中有足够数据，返回 30 个节点, 45 条边, 80 条路径
- **Agent分析**: 分析子图后，返回 `status: "NEED_MORE_CONTEXT"`, `missing_information: ["C", "D", "E"]`
- **实体匹配**: 
  - "C" → 匹配到节点 [C1, C2]
  - "D" → 匹配到节点 [D1]
  - "E" → 匹配到节点 [E1, E2]
- **输出seed_ids**: [A, B, C1, C2, D1, E1, E2] (7个) ← **累积：保留A, B，新增C1, C2, D1, E1, E2**

### 迭代2
- **输入seed_ids**: [A, B, C1, C2, D1, E1, E2] (7个) ← **包含迭代1的所有节点**
- **Neo4j查询**:
  - 一跳查询：`WHERE seed.cui IN [A, B, C1, C2, D1, E1, E2] LIMIT 175`
  - 两跳查询：`WHERE seed.cui IN [A, B, C1, C2, D1, E1, E2] LIMIT 350`
- **查询限制**: 最多175条边, 最多350条路径
- **实际返回**: 假设返回 100 个节点, 150 条边, 280 条路径 ← **显著增长**（因为查询了更多节点的邻居）
- **Agent分析**: 返回 `status: "NEED_MORE_CONTEXT"`, `missing_information: ["F", "G"]`
- **实体匹配**: 
  - "F" → 匹配到节点 [F1, F2, F3]
  - "G" → 匹配到节点 [G1]
- **输出seed_ids**: [A, B, C1, C2, D1, E1, E2, F1, F2, F3, G1] (11个) ← **继续累积**

### 迭代3
- **输入seed_ids**: [A, B, C1, C2, D1, E1, E2, F1, F2, F3, G1] (11个) ← **包含所有之前的节点**
- **Neo4j查询**:
  - 一跳查询：`WHERE seed.cui IN [A, B, ..., G1] LIMIT 275`
  - 两跳查询：`WHERE seed.cui IN [A, B, ..., G1] LIMIT 550`
- **查询限制**: 最多275条边, 最多550条路径
- **实际返回**: 假设返回 200 个节点, 250 条边, 480 条路径 ← **继续增长**
- **子图文本**: `format_subgraph_as_text()` 将所有节点、边、路径转为文本
- **Token数量**: 可能超过 131072，导致API调用失败 ❌

## 6. 解决方案建议

### 方案1: 限制子图大小
在`format_subgraph_as_text()`中添加截断逻辑，只输出前N个节点/边/路径。

### 方案2: 增量查询
只查询**新增seed_ids**的邻居，而不是所有seed_ids的邻居。

### 方案3: 去重和过滤
在累积seed_ids时，不仅检查是否已存在，还要检查是否与问题相关。

### 方案4: Token计数和截断
在构建prompt前计算token数量，如果超过限制则截断子图文本。

### 方案5: 使用摘要
对于大型子图，使用LLM生成摘要而不是完整文本。
